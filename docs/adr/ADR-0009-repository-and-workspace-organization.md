# ADR-0009 — Repository and Workspace Organization

## Status
**Accepted** (2026-07-10)

## Context
With the Canonical Object Model ratified (ADR-0007) and TypeScript/Node.js chosen as the implementation language (ADR-0008), repository initialization requires a concrete, executable repository structure, toolchain, and documentation-governance model — not left as an open choice for whichever agent or engineer scaffolds the repository. `docs/process/repository-design-specification.md` is the full reasoning document; this ADR ratifies its structural decisions at the architectural level so they carry the same authority and stability as ADR-0001–0008.

## Decision
- **Single private GitHub repository, monorepo.** Nine packages (`@aios/core`, `@aios/objects`, `@aios/work-hierarchy`, `@aios/containers`, `@aios/agents`, `@aios/tools`, `@aios/learning`, `@aios/orchestration`, `@aios/founder`), matching `docs/engineering/runtime-interfaces.md`'s component boundaries and dependency graph exactly — no change to the boundaries, only to naming and physical layout.
- **Toolchain:** pnpm (package manager, workspace protocol, strict `node_modules` layout), Turborepo (build orchestration, dependency-graph-aware caching), Biome (lint/format), Vitest (test runner, one workspace spanning per-package unit tests plus centralized `tests/integration` and `tests/conformance`), Zod (schema/validation source, with JSON Schema generated from it — see §1.10 below).
- **Two-tier documentation, enforced by directory:** `docs/adr/` + `docs/architecture/` (the certified corpus — ADR-0001 through ADR-0009, the Specification, Conformance Standard, Appendices, Normative Amendment 001) changes only via a new or amending ADR and is `CODEOWNERS`-gated. `docs/engineering/` (Canonical Object Model, schemas design intent, runtime interfaces, state machines, API contracts, developer reference, implementation roadmap, implementation playbook) is living reference, changed via normal PR review, escalating to a new ADR only if a change reveals `docs/architecture/` is actually wrong. `docs/process/` (changelog, certification report, AI development plan/workflow, repository design spec) is append-mostly status record. `docs/archive/` is frozen historical material.
- **§1.10 — Generated vs. manual artifacts:** `packages/core/src/schema/*.ts` (Zod definitions) is the single hand-edited source of truth, replacing the previous hand-maintained parallel JSON Schema + TypeScript pair (`docs/archive/object-schemas-superseded.md`) that could silently drift against each other. `schemas/generated/*.json` is generated from it via `zod-to-json-schema`, is git-tracked for PR-visible diffs, and is never hand-edited — enforced by `schema-check.yml` failing the build on any diff between committed and regenerated output.
- **Versioning:** software semver from `0.1.0` via Changesets, explicitly distinct from "AIOS Architecture Version" (ADR-numbered) — the two axes will diverge in practice.
- **Git workflow:** trunk-based, `main` always buildable (CI-enforced), no long-lived `develop` branch, per-package or per-vertical-slice short-lived branches, Conventional Commits, an AI-attribution trailer (`Implemented-by: Claude` / `Implemented-by: Ollama/<model>`) on AI-authored commits.

## Rationale
- The dependency graph in `docs/engineering/runtime-interfaces.md` §4 already exists conceptually; Turborepo and pnpm workspaces make it operationally real rather than requiring a new design.
- The Zod-first schema decision eliminates an entire class of drift defect (two hand-maintained artifacts silently disagreeing) instead of policing it with a CI check after the fact — a strictly better fix than the drift-detection approach considered and rejected during repository design.
- The two-tier documentation split gives the ten-session reconciliation effort's stability (`docs/process/reconciliation-changelog.md`) a physical, `CODEOWNERS`-enforced location to protect, rather than relying on convention alone.
- Trunk-based git with no `develop` branch is consistent with ADR-0003's own reasoning for deprecating premature governance apparatus (SEF/ADM/SAF, ARB/ERB/CRB) — process ceremony should match actual team size and project stage, not be speculatively scaled ahead of need.

## Consequences
- Every subsequent implementation PR must respect the `docs/architecture/` vs. `docs/engineering/` boundary: a change that only refines an engineering document is normal review; a change that contradicts `docs/architecture/` requires a new or amending ADR first.
- `docs/engineering/developer-reference.md` currently predates the Zod-as-source decision and needs a content update to reference it — tracked as a first post-initialization PR, not done as part of this ADR or the repository initialization it ratifies.
- The two largest architecture documents (`docs/architecture/specification.md`, `docs/architecture/conformance-standard.md`) are flagged as future candidates for per-Part splitting to improve PR reviewability. This is explicitly deferred, not part of this decision — splitting them now risks introducing errors into certified content for a reviewability benefit that doesn't matter until someone is actively editing those files.
- `.github/CODEOWNERS` names a placeholder (`@founder`) pending the repository owner substituting their real GitHub handle — the gating is inert until that substitution happens.

## Superseded Decisions
- `PROJECT-MANIFEST.md`, `IMPLEMENTATION-HANDOFF.md`, and `PROJECT-ADDITION-PACKAGE.md` (preserved at `docs/archive/prior-manifests/`) are superseded by this ADR and by `docs/process/repository-design-specification.md`, which it ratifies — their repository-structure recommendations predate and in places conflict with the structure adopted here (notably: flat `schemas/` vs. `schemas/generated/`, and a top-level `tests/unit/` vs. this decision's per-package colocated unit tests). `docs/engineering/implementation-roadmap.md` §1 contains a similarly superseded repository tree; it is annotated in place with a pointer to this ADR and to `docs/process/repository-design-specification.md` rather than rewritten, per this project's established no-silent-discard policy.
